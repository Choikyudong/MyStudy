# 네트워크 기초

## TCP/IP 프로토콜 스위트 (dod 모델)
기존 OSI 7계층을 조금 더 단순하게 표현한 모델로,
- 응용(Application)  
  OSI 5, 6, 7 계층을 묶은 영역이다.    
  프로토콜 : HTTP, FTP, SMTP, DNS 등  
  단위 : 데이터
- 전송(Transport)  
  종단 간 (End-to-End) 신뢰성 있는 전달  
  프로토콜 : TCP, UDP  
  단위 : 세그먼트
- 인터넷(Internet)  
  목적지까지 경로 설정 (라우팅)  
  프로토콜 : IP, ICMP  
  단위 : 패킷
- 네트워크 액세스(Network Access Layer)  
  기존의 1, 2 계층을 묶은 영역  
  장비 : 케이블, 허브, 랜칩  
  단위 : 비트
> 기존 모델에 비해 조금 더 심플해져 현재는 해당 모델로 많이들 표현을 한다.

## 캡슐화/역캡슐화
데이터 전송을 위해 상위 계층에서 하위 계층으로 내려가면서,  
각 계층별로 필요한 **정보**들을 데이터에 덧붙이는 과정을 **캡슐화**라고 한다.

반대로 받는 쪽이 하위 계층에서 상위 계층으로 올라가면서 각 계층에 필요했던,  
**정보**들을 제거해나가는데 이것은 **역캡슐화**라고 한다.

아래는 웹사이트 접속 기본적인 흐름이다.
1. 응용 계층    : 요청 데이터 생성 (예: HTTP GET 요청)
2. 전송 계층    : 위 데이터에 TCP 헤더 붙임 (포트 번호, 순서번호 등) → 세그먼트
3. 인터넷 계층  : 세그먼트에 IP 헤더 붙임 (출발지/목적지 IP) → 패킷
4. 네트워크 접속 계층 : 패킷에 헤더 + 트레일러 붙임 (MAC 주소, 오류검출) → 프레임
5. 물리 계층    : 프레임을 실제 전기/광 신호로 변환해서 전송

여기서는 http://info.cern.ch/ 사이트를 기준으로 `와어이샤크`를 이용해 흐름에 대해 간단히 알아보자.
> info.cern.ch는 팀 버너스리가 만든 세계 최초의 웹사이트로  
현재는 원본 형태를 보존하여 누구나 접속할 수 있다.  
와이어샤크(Wireshark)란 세계 표준 네트워크 패킷 분석기이다.

### 흐름 살펴보기
사이트 `http`로 캡쳐 한뒤 접속하면 아래와 같이 볼 수 있다.
```text
GET / HTTP/1.1                              192.168.x.x → 188.184.67.127
HTTP/1.1 200 OK (text/html)                 188.184.67.127 → 192.168.x.x
GET /favicon.ico HTTP/1.1                   192.168.x.x → 188.184.67.127
HTTP/1.1 200 OK (image/vnd.microsoft.icon)  188.184.67.127 → 192.168.x.x
```
- 192.168.x.x = 접속한 PC의 사설IP
- 188.184.67.127 = info.cern.ch 서버의 공인 IP

여기서는 조금만 더 파고들어 보자.
```text
GET / HTTP/1.1                              192.168.x.x → 188.184.67.127
HTTP/1.1 200 OK (text/html)                 188.184.67.127 → 192.168.x.x
```
영역을 간단하게 살펴보자.
> favicon(favorite + icon)의 합성어로 사이트 브랜드의 시각화를 위해   
사이트 운영자가 등록해두는 이미지 파일로 접속시 브라우저가 자동으로 
도메인/favicion.ico 경로에 `favicon`을 요청하는게 관례이다.

### 캡슐화 흐름 정리
각 계층은 자기 바로 아래 계층에만 데이터를 넘기면 된다.  
HTTP는 TCP만 알면 되고, TCP는 IP만 알면 되고, IP는 MAC만 알면 된다.  

그래서 위에서 아래로 내려가며 헤더가 한 겹씩 붙는 것 — 순서 자체에 특별한 이유가 있다기보다,   
"한 단계 아래만 신경 쓴다"는 설계 원칙의 결과다.

각 헤더는 예외 없이 **"다음 계층이 뭔지 예고하는 필드"** 를 갖고 있다.  
이게 캡슐화가 실제로 동작하는 방식이다.
```text
Ethernet의 Type: IPv4        → "다음은 IP다"
IP의 Protocol: TCP           → "다음은 TCP다"
```

#### 계층별 핵심
##### 네트워크 접속 계층
```text
Src: [내 랜카드 MAC] → Dst: [공유기 MAC]
Type: IPv4
```
- 역할: 최종 목적지가 아니라 "바로 다음 한 걸음(공유기)"까지만 책임짐

##### 인터넷 계층 (IP)
```text
Src: 192.168.50.164 → Dst: 188.184.67.127   ← 최종 목적지, 끝까지 안 바뀜
Protocol: TCP
TTL: 128
```
- 역할: 라우팅 — 이 패킷이 최종적으로 어디까지 가야 하는지 결정
- MAC과 대비되는 지점: MAC은 한 홉마다 바뀌지만 IP는 출발지→목적지까지 고정
- 나머지 필드(DSCP, ECN, Fragment 관련)는 특수 상황 아니면 무시

##### 전송 계층 (TCP)
```text
Src Port: 52015 → Dst Port: 80
Sequence Number: 1, Acknowledgment Number: 1
Flags: PSH, ACK
```
- 역할: 신뢰성 있는 전달 — 순서번호/ACK로 "유실 없이, 순서대로" 왔는지 관리
- Flags는 이 패킷의 "의도"를 나타냄 (ACK=응답 확인, PSH=바로 위로 올려보내라)

##### 응용 계층 (HTTP)
```text
GET / HTTP/1.1
Host: info.cern.ch
```
- 역할: 원래 의도했던 진짜 내용. 여태 감싸여 있던 걸 다 벗기면 이것만 남음
- Host가 IP와 별도로 필요한 이유: 한 서버(한 IP)에 여러 도메인이 같이 있을 수 있어서,
  "그 서버 안에서 어느 사이트냐"를 구분해야 함
